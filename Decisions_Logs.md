## What I built
- Module 1 - Admin Portal · Order Submission (Order Summary after submission in an order details page)
- Module 2 - Technician Portal · Service Job
- Module 3 - WhatsApp Notification Trigger
- AI Module - Operations Query Window

## Stack decision — Next.js over Vite

**Why:** The AI module needs the LLM API key held server-side. A Vite build is static files
handed to the browser, so any API call from it ships the key to the client where anyone can read
it from devtools — env vars don't help, Vite inlines them at build time. Next.js route handlers
(`src/app/api/*/route.ts`) run on the server as part of the same project: one build, one deploy,
one config, and `process.env` there never reaches the browser. Vite + separate Vercel functions
would also work but is two systems bolted together.

**Traded away:** Nothing meaningful at this scale. Next is heavier than Vite and the
server/client component boundary is a real source of bugs — I've shipped App Router before, so
that cost was low for me.

**Stack:** Next 16.3.3 · React 19.2.8 · Tailwind v4 · shadcn/ui · Supabase (Postgres + Storage) · Vercel.

## Notification channel — WhatsApp deep link, not an API

**Why:** The spec asks for "a deep-link URL with a pre-filled message." `wa.me/<phone>?text=<msg>`
opens WhatsApp with the message typed but **unsent** — a human taps send. No vendor account, no
API key, no per-message cost.

**Traded away:** It isn't an automated send. Considered Twilio/Movider/Resend and rejected them:
more than the spec asked for, and a paid dependency for a demo.

**Limitation:** Requires a human in the loop; nothing is delivered if nobody taps send.

## Data model — decisions log

(filled in as we go)

### Order numbers: internal PK vs public number

Two columns. `id uuid` is the primary key foreign keys point at. `order_no text` is what humans
read — `ORD-01001` — used in the UI, search, and the WhatsApp message. A UUID in a customer's
WhatsApp ("Job a3f8b2c1-9d4e-... has been completed") is unusable, so the two jobs are separated.

`order_no` is generated by a Postgres **sequence** in a column DEFAULT. `nextval()` is atomic and
non-transactional: two admins submitting in the same millisecond get different numbers. The naive
`SELECT count(*)+1` fails here — both sessions read the same count and write the same number.
A rolled-back insert leaves a **gap** in the numbering, because sequences don't roll back. Gaps
are acceptable; duplicates are not.

**Considered and rejected:** a 24-bit Feistel cipher (format-preserving encryption) producing an
unguessable 5-char Base30 code. It defends against order-number enumeration — a real concern for
a public-facing system. Rejected as
over-engineering for demo project, and because a sequence is something I can fully explain
and debug. **Concern I'm accepting:** sequential numbers leak volume — anyone seeing two order
numbers can infer how many jobs happened in between. That's the trade-off I took for quick implementation, in real-life production, it will be an encryption algorithm like 24-bit Feistel cipher that will defend against order-number enumeration.

### `final_amount`: generated column, and its known flaw

`final_amount` is a **generated stored column**: `quoted_price + extra_charges`, computed by
Postgres and written into the row. It can never disagree with its inputs, is never set by hand,
and is a real column so the AI module can `SUM()` and index it.

**Known limitation (deliberate).** A generated column tracks its inputs *forever*. Editing
`quoted_price` on a long-closed order silently recomputes `final_amount`, so a job quoted 250 +
80 extras and paid in full at 330 becomes "owed 340, paid 330" — a phantom balance on a settled
job. The underlying mismatch: `final_amount` is derived, but an invoice is a **historical fact**
that should freeze at completion.

Accepted for this build. In production I'd reject edits to `quoted_price` once status passes
`job_done`, or snapshot the amount at completion.

### `completed_at` and `status`: one write path

`status` and `completed_at` both encode "this job is done". Nothing in the schema forces them to
agree, and a bug that sets one without the other produces two screens showing different truths —
the manager's review queue filters on `status`, the AI's "completed today" filters on
`completed_at`.

`completed_at` still earns its place (it carries *when*, which `status` can't express — and all
three of the spec's example AI questions are time-windowed). The fix isn't dropping the column,
it's removing the chance to disagree: **status is never written by application code.** A database
trigger sets `status` and `completed_at` in the same statement, so they cannot drift.

This is the same duplication I removed earlier by dropping an `is_completed` boolean — that one
carried no information `status` didn't already have, so it was deleted outright.

### Technicians are deactivated, never deleted

`users.is_active` soft-deletes. `orders.assigned_tech` is `on delete restrict`, so a hard delete
that would orphan completed jobs fails loudly instead of silently nulling history — `on delete
set null` would have destroyed exactly the data the AI module reports on ("which technician
completed the most jobs"). Consequence: the UI offers **Deactivate**, not Delete, and the
technician dropdown filters on `is_active = true`.

### Re-opened jobs: one order, not two

A manager rejecting a completed job sends it back to the same order (`job_done -> in_progress`),
it does not create a second order. Considered creating a new order and rejected it: the customer's
single visit would then count twice in "how many jobs were completed today", and the WhatsApp
message (`Job {{Order ID}} has been completed`) would have to name one of two order numbers.

**Known limitation (deliberate).** Re-completing overwrites the previous `work_done`,
`tech_remarks`, `extra_charges` and `completed_at` — the first attempt's detail is lost. What
survives is the `actions` row recording that a rejection happened, by whom, when, and why.
`completed_at` is explicitly cleared on rejection so it never disagrees with `status`; the
timing of the first attempt is recoverable only from `actions`.

The fuller fix is to make completion its own table (one order -> many service reports), keeping
every attempt. That was cut for time, not overlooked.

### Status is not writable by the application

The app never sets `orders.status`. It inserts a row into `actions`, and a database trigger
validates the transition against a table of legal moves and applies it. A second trigger on
`orders` raises if `status` changes outside that path.

Why this and not status changes in React or the API route: with three call sites able to write
status there are three places to get it wrong, and no way to stop a fourth appearing later.
Here an illegal move raises an exception instead of silently corrupting state, `status` and
`completed_at` are written in one statement so they cannot drift, and the audit trail the spec
asks for ("key actions should be traceable") is produced by the mechanism rather than depending
on a developer remembering to log it.

**Cost:** triggers are invisible from application code. When status doesn't change, nothing in
the TypeScript explains why — the answer is in a migration file. Worth it for a state machine
this central; I would not use triggers for ordinary business logic.

**`in_progress` is entered by an explicit "Start job" tap.** The alternative was firing `started`
automatically when the technician opens the job, saving one tap — attractive because Module 2 says
to optimise for field speed. Rejected: opening a job to check an address or realise it is the
wrong job would then mark it In Progress, so the state would mean "someone looked at this" rather
than "a technician is working on this". A manager watching live status needs the second meaning.
One extra tap buys a state that carries information.

Completion is only legal from `in_progress`, so `in_progress` is always passed through rather than
being an optional state some orders skip.

### Enums vs text + check vs lookup table

`status`, `role` and `action_type` are Postgres **native enums**. `service_type` is `text` with a
`CHECK`. That split is deliberate, and the question that decides it is: *does application code
branch on this value, or do humans manage it as data?*

**Code branches on it -> enum.** The status trigger's `CASE` is a literal list of the legal
statuses and action types; a value that exists in the database but not in that `CASE` is a bug,
so rigidity is the feature. Changing the set means changing the state machine, which means a
deploy anyway, so needing DDL costs nothing extra. Enums also make Supabase's type generator emit
real TS union types (`"new" | "assigned" | ...`) instead of `string`, so a typo like
`'inprogress'` fails at compile time rather than silently matching nothing at runtime.

**Humans manage it -> lookup table.** `service_type` is business data: ops will want to add a
service line, retire one, attach a display label and a default price, and order the dropdown.
None of that fits in a type or a constraint. It stays `text + check` here only because a lookup
table is more machinery than a two-day build needs; in production it becomes a table with an FK,
and adding a service becomes an `INSERT` rather than a migration.

**Why not `text + check` for all of them.** It has an enum's rigidity (DDL to change) without an
enum's type safety or introspection — arguably the worst of the three for a closed set. It is the
default because it is the easiest thing to write, which is exactly why it deserves a second look.

**Enum costs, accepted:** values cannot be removed (only renamed, via `ALTER TYPE ... RENAME
VALUE`), and `ALTER TYPE ... ADD VALUE` cannot add and then use a value in the same transaction —
awkward when pasting a multi-statement migration into the SQL editor. Neither bites a set this
stable.

**Ordering, not used:** enum values are comparable in declaration order, so `status >= 'job_done'`
would work. Deliberately unused — `rejected` moves an order *backwards* (`job_done -> in_progress`),
so these states are not linearly ordered and treating them as ordered would encode a falsehood.

**What the enum conversion actually bought, concretely:**

1. **Typos fail loudly instead of silently.** `where status = 'inprogress'` against a `text`
   column returns zero rows and no error — an empty dashboard with nothing to debug. Against an
   enum it raises `invalid input value for enum order_status`. This is the single biggest win:
   it converts a silent wrong-answer bug into a loud one.
2. **Compile-time safety in React.** `supabase gen types typescript` emits
   `"new" | "assigned" | "in_progress" | "job_done" | "reviewed" | "closed"` instead of `string`,
   so every status comparison in the app is checked before it runs.
3. **The dropdown cannot drift from the schema.** `select unnest(enum_range(null::order_status))`
   returns the legal values, so UI filters are derived from the database rather than a hardcoded
   TypeScript array that someone forgets to update.
4. **Rejected before the trigger runs.** An invalid `action_type` fails at the type boundary on
   insert, not inside `actions_apply_transition()`. Bad values never reach the state machine.
5. **Cheaper storage and comparison** on `orders.status`, which is indexed and filtered on nearly
   every query: 4 fixed bytes and integer comparison, versus a variable-length string compare.
   Marginal at this scale, real at production volume.
6. **The schema documents the state machine.** `\dT+` lists the full vocabulary of statuses and
   actions in one place, instead of it being buried in a `CHECK` constraint on one column.

### Row Level Security: deny-all, and all access server-side

Supabase publishes every `public` table over PostgREST and grants the `anon` role privileges on
them by default. The anon key is `NEXT_PUBLIC_`, so it ships in the browser bundle in plain text.
With RLS off, anyone who views source can `POST /rest/v1/orders` directly and write to the
database — bypassing the status trigger's guard, the CHECK constraints, and every rule the
application enforces. None of that is reachable if the request never goes through the application.

**Decision:** RLS enabled on `users`, `orders` and `actions` with **no policies defined** —
deny-all for `anon` and `authenticated` — plus an explicit `REVOKE` as defence in depth. All
reads and writes happen in Next.js server code using `SUPABASE_SERVICE_ROLE_KEY`, which bypasses
RLS and never reaches the browser. There is deliberately no browser-side Supabase client.

**Rejected: RLS policies keyed to the role switcher.** With no real auth, `auth.uid()` is null and
any role a policy could read is supplied by the client. A policy the client satisfies by lying is
worse than no policy, because the dashboard then reports the table as protected. Honest deny-all
beats decorative rules.

**Side benefit:** the "all queries go through the server" convention becomes enforced rather than
aspirational. A component that queries Supabase directly does not fail code review — it fails at
runtime with zero rows, immediately and visibly.

**Limitation (stated plainly).** Authorization — only Admin assigns, only the assigned technician
completes, only Managers review — is checked in server code against a role the client asserts.
The database is protected from the public internet; it is not protected from a user who claims to
be someone else. With real auth the role would come from a verified session, and RLS policies
keyed on `auth.uid()` would enforce the same rules a second time at the data layer.

### Testing the state machine

pgTAP is the standard way to test Postgres triggers and constraints, and Supabase supports it via
`supabase test db` — but it needs a local Docker stack that a two-day build cannot justify setting
up. Instead: a single idempotent SQL script, `supabase/tests/state_machine_test.sql`, wrapped in
`begin` / `rollback` so it leaves no data behind and can be re-run any number of times.

Nineteen assertions, all passing. They cover the parts of the system that application code can
never see — which is exactly why they are the parts worth testing:

- defaults (`status = 'new'`) and the generated `final_amount` before and after extra charges
- every legal transition in the table: assigned -> started -> completed -> reviewed -> closed
- **illegal transitions raise**: reviewing a `new` order, completing one that was never started
- `orders.status` cannot be written directly — the UPDATE guard fires
- `rejected` moves the order back to `in_progress` **and clears `completed_at`**, proving the two
  columns are written in one statement and cannot drift
- the trigger stamps `from_status` / `to_status` on the audit row without the caller supplying them
- the audit trail accumulates exactly one row per action (7 after a full reject-and-redo cycle)
- `order_docs` rejects a 7th file; the enum rejects an unknown `action_type`; a technician with
  orders cannot be hard-deleted

Errors surface as intended rather than as generic failures — e.g.
`illegal transition: cannot completed an order in status assigned`, and
`orders.status is not directly writable (attempted job_done -> closed)`.

**Why this order:** the seed data is generated by driving orders through the state machine rather
than inserting statuses directly, so the machine had to be verified before anything depended on it.
A bug found in a 40-line test is cheaper than one found in a 36-order seed that half-worked.

### Verifying the tests themselves (mutation check)

Twenty-four passing assertions prove that something ran; they do not prove any assertion *could*
have failed. So each rule was deliberately broken and the suite re-run, to confirm the right
assertion went red.

That exercise found a bug — in the test harness, not the schema. Breaking the
"only the assigned technician may start a job" rule made assertion 21's insert **succeed** when it
should have raised. The wrongly-succeeded insert advanced the order to `in_progress`, so the *next*
step crashed with an unrelated error and the whole script aborted. A broken rule was reporting the
wrong failure in the wrong place.

Fix: every expect-raise assertion now raises its own `ASSERT_FAIL` exception if the statement
unexpectedly succeeds. In PL/pgSQL an exception rolls back its subtransaction, so a statement that
should have failed leaves no side effect behind, and the assertion records a clean `false` instead
of poisoning everything after it. Re-running against the same mutant then produced exactly one red
row and 23 green.

Two assertion pairs exist for the same reason — one alone would pass vacuously:

- **9 then 13**: `completed_at` is set on completion, then cleared on rejection. If the trigger
  never set it at all, 13 would still pass, because null is null.
- **23 then 24**: a deactivated manager cannot review, then a reactivated one can. Without 24, any
  unrelated failure of manager reviews would make 23 look like proof the `is_active` check works.

The general lesson, and the reason it is worth writing down: a test that cannot fail is worse than
no test, because it converts an unverified assumption into a trusted one.

## Module 1 — Admin portal

**Order list.** Filtering, search and sort run in Postgres, driven by `searchParams`, not in the
browser. Client-side filtering would have been faster to build at this data volume, but the
server-side version buys three things: the filtered view is a shareable, bookmarkable URL that the
back button understands; the browser never receives rows it will not display; and the queries use
the indexes created in 0001. Searching by technician costs a second query — technician name lives
on the joined `users` table and PostgREST cannot `ILIKE` across an embed — so matching technicians
are resolved to ids first, then folded into the main `OR`.

**Order creation is one RPC, not four writes.** Creating an assigned order means inserting the
order, logging `created`, setting `assigned_tech`, and logging `assigned`. supabase-js cannot wrap
those in a transaction, so a failure partway would leave an order with a technician attached but
status still `new` — a state the state machine says cannot exist. `create_order()` (0005) does all
four inside a Postgres function, which is implicitly one transaction.

Writing that function surfaced a gap in the role checks: 0004 validates the **actor** (only an
admin may assign) but nothing validated the **target**, so an order could have been assigned to a
manager. Authorization and data validity are different kinds of rule, and a file full of
authorization checks had no opinion about the second. The target check lives in `create_order()`.

**Validation runs twice, from one schema.** The browser pass gives immediate feedback; the server
action pass is the one that matters, because a direct POST, a replayed request, or a form submitted
with JavaScript disabled never runs the browser code. Both import the same zod schema *and* the
same `FormData` mapping from `lib/validation.ts` — duplicating the mapping would be the obvious
place for the two layers to drift apart.

Phone numbers accept either local (`012-345 6789`) or international (`60123456789`) input and are
normalised to `60…` on save. That is not tidiness: Module 3's `wa.me` deep link requires exactly
that form, and normalising at the edge means nothing downstream has to guess which format a row
holds.

**Known limitation.** The admin role check exists in both the server action and the database
trigger. That is deliberate — the trigger is unbypassable, the TypeScript check turns a Postgres
exception into a sentence a human can read — but it is two places to keep in step, and the
duplication is only safe because the trigger is the authority.

### Role scoping, and the silent-admin bug I shipped first

The first version of the order list was not scoped at all. Switching to a technician still showed
all 36 orders, including other technicians' jobs — `role` was used only to hide the "New order"
button, which is decoration, not a restriction. Alongside it, `getCurrentUser()` fell back to the
seeded **admin** whenever the session cookie was missing or pointed at a deleted user. That is the
worst possible default: the failure mode granted *more* access than intended.

Both are fixed, and the fix is placed deliberately.

**Scoping happens in the query, not the view.** `listOrders()` and `getOrder()` both take the
viewer and add `assigned_tech = <viewer>` for technicians. Doing it in the rendering would have
left the detail page wide open — a technician could paste any order id into the URL and read it
while the list *looked* like it was protecting the data. Scoping belongs wherever rows are
fetched, not once at the top.

**No fallback identity.** `getCurrentUser()` now returns `null` and callers use `requireUser()`,
which redirects to `/switch-role`. Choosing a user is an explicit screen rather than an implicit
default, which also makes the demo self-explanatory: a reviewer opening the app is shown, not
told, that three roles see different views. `switchUser()` validates the id against the database
before writing the cookie, so the rest of the app can assume the cookie names a real active user.

**Each role opens on the view that matches its job:** admin on `New` (unassigned work waiting to
be assigned), manager on `Job Done` (the review queue), technician on everything assigned to them.
The default is applied as a **redirect**, so the URL always states what is being shown and the
Clear button has something coherent to clear. That forced `all` to become an explicit URL value —
an absent `status` means "just arrived, apply the default", which is a different state from
"deliberately showing everything".

**A bug worth recording.** That sentinel was first exported from the filters component, which
carries `'use client'`. Importing it into a server component did not yield the string — it yielded
a client *reference*, and the resulting error text was serialised straight into the query string.
Values shared across the server/client boundary have to live in a module that belongs to neither
side; it now sits in `lib/types.ts`.

**Still a mock.** Scoping is enforced against the user the cookie claims to be. It is a correct
data boundary given a trusted identity, and there is no trusted identity here — with real auth the
same code becomes a real restriction, and RLS policies keyed on `auth.uid()` would enforce it a
second time at the data layer.

## Module 2 — Technician portal

### No scheduling: "my open jobs", not "today's jobs"

The technician list shows every job assigned to them that is not finished —
`assigned` and `in_progress` — rather than jobs scheduled for today.

I initially specified "today", then found the schema cannot answer it: orders
record `created_at` and `completed_at`, but nothing records when a job is
*meant* to happen. There is no appointment slot, no due date. "Today's jobs" is
not a query this data model supports.

Adding a `scheduled_for` column would have meant a migration, a backfill of the
seeded orders, and new fields in the admin form and list — a scheduling feature
in a system that has no scheduling anywhere else. The spec asks only that
"technicians view assigned jobs", so the requirement I invented was stricter
than the one I was given.

For a technician with a handful of open jobs, the open list *is* the day's work.

**What a real deployment would need:** a scheduled date and time window per
order, so the admin can plan routes, the technician sees a running order for the
day, and "overdue" becomes a state worth surfacing. That is a genuine missing
capability rather than a shortcut — but it is a feature, not a fix, and it was
not asked for.

### File upload: limits, and where each one is enforced

Per-type limits, defined once in `UPLOAD_RULES` (`lib/uploads.ts`): images and PDFs 10 MB, video
50 MB, six files per job. A photo and a video are not the same problem — a phone photo is 2-8 MB
while 30 seconds of 1080p is 50-100 MB, so a single cap generous enough for video is far more
headroom than an image needs.

That module is imported by both the browser picker and the server action, so the two layers cannot
disagree about what is allowed. Duplicating the numbers would be the obvious place for them to
drift, the same reason order validation shares one zod schema.

**Enforced three times, each catching what the others cannot:**

1. **The picker** — so a technician learns before spending upload time on a phone connection.
2. **The server action** — a direct call never runs the picker.
3. **The bucket** (`file_size_limit`, `allowed_mime_types`, migration 0006). This one matters more
   than it looks. A signed upload URL is minted for a **path**, not a size, so the server validates
   a *declared* size, not the actual bytes: a client could request a token claiming a 5 MB image and
   then PUT 40 MB to it. Only the bucket sees real bytes. A bucket has one size limit and cannot
   express per-type rules, so it holds the highest (50 MB) as a hard ceiling.

**Known limitation:** between the app's 10 MB image rule and the bucket's 50 MB ceiling there is a
window where a client that lies about a file's size could store an oversized image. Closing it
would mean a second bucket per type, or checking the object's real size after upload and deleting
it if it overruns.

### Uploads are shaped by the device, not by the desktop default

The obvious MIME list is `jpeg / png / mp4`. That list rejects most of the field.

**`image/heic` and `image/heif`** are the default camera formats on every iPhone since 2017, and
**`video/quicktime`** (`.mov`) is what iPhone video produces. Omitting them means a technician's
entire camera roll is refused. They are accepted.

Extensions are never derived from MIME type: `storagePath()` sanitises the **original filename**,
so `IMG_4821.heic` is stored as `.heic` rather than having an extension reconstructed from a
lookup table that would have to be kept in step with the MIME list.

**Accepting a format and being able to preview it are different questions.** Only Safari renders
HEIC in an `<img>`; Chrome, Firefox and Edge show a broken image. So `canPreview()` separates the
two, and HEIC files will be shown as a file card with an Open link rather than an inline thumbnail
— the browser then downloads them or hands them to the OS.

**Not built (pending):** `order_docs` is stored but not yet rendered anywhere outside the
technician's own upload list, so a manager cannot currently see the proof attached to a completed
job. That needs signed read URLs (`createSignedUrl`, because the bucket is private) plus the
preview/card split above.

**Considered and rejected:** converting HEIC to JPEG on upload (heic2any in the browser, or sharp
server-side). It would give real thumbnails everywhere, at the cost of an image pipeline, a second
stored derivative per file, and a new way for an upload to fail — for a preview convenience the
spec never asks for.

### Showing uploaded files to the reviewer

Files are stored in a **private** bucket with no storage policies, so nothing is readable by URL
alone. The order detail page mints short-lived signed read URLs server-side with the service_role
key (`createSignedUrls`, one hour) — the browser receives a time-limited link to one specific
object, never a credential that would let it list or fetch anything else.

One hour is a compromise in both directions: long enough to read a page and open a file without
links dying mid-review, short enough that a URL pasted into a chat is not a permanent public link
to a photo of a customer's home. A file that fails to sign renders as "Unavailable" rather than
throwing, so one missing object cannot blank out the whole review page.

**Three renderings, because "accepted" and "displayable" are different questions.** JPEG, PNG and
WebP become inline thumbnails; MP4 and WebM become inline players; HEIC, HEIF, `.mov` and PDF
become a file card with an Open link. HEIC is what forces the split — it is the default iPhone
camera format so it has to be accepted, but only Safari renders it in an `<img>`. Putting one in a
thumbnail grid gives every Chrome and Firefox user a broken image, which reads as data loss rather
than a format limitation. The same logic applies to `.mov` against `<video>`.

Deliberately plain `<img>` rather than `next/image`: these are private, signed, expiring URLs, and
routing them through the image optimiser would mean caching customers' photos on a CDN.

**Limitation:** thumbnails are the full-size originals scaled by CSS, so a review page with six
10 MB photos downloads 60 MB. Real thumbnails would need a derivative generated at upload time —
an image pipeline that was out of scope here, and the same one that would have solved HEIC preview.

## Module 3 — WhatsApp notification

### The trigger condition is a state, not an event

The spec says *"Trigger Condition: status = Job Done"*. The obvious reading is an event —
completion succeeds, so fire a notification — and that reading produces a worse system.

Built as an event, the link exists only in the render that follows a successful `completeJob`.
A technician whose phone drops signal between the write landing and the page painting has an
order that is permanently `job_done` with a customer who was never told, and nothing anywhere
remembers that. No re-send, no second chance, and no way for anyone else to pick it up.

Built as a state — *any order whose `completed_at` is set carries a notify link, computed from
the row at render time* — it survives a crash, a refresh, a different device and a different
day. Idempotent and re-sendable, and it still appears the instant the job completes, because
"the instant of completion" is just the first time someone looks at a row that qualifies.

**There is deliberately no database trigger, webhook or queue**, which is worth stating because
"back-end trigger logic" invites one. A deep link has no send step. The notification *is* a human
tapping a link, and a human cannot be enqueued. A trigger only earns its place once something
automated consumes it — the WhatsApp Business API, a vendor account, per-message cost — which is
out of scope here. So the honest architecture is a predicate on a row, and a predicate can be
true many times where an event fires once.

### Keeping the link reachable, which needed a change to the technician's list

The design above is worthless if the state is only observable in one fleeting place, and that was
exactly the situation. Once an order reached `job_done` it left the technician's world entirely:
`listMyJobs` returns only `assigned` and `in_progress`, `/jobs/<id>/complete` refuses anything
else, and `/orders` is a desk view. The order became unreachable for the person who did the work.

So `/jobs` gained a **Recently completed** section. It also fixed a live bug found on the way in:
`completeJob` redirected to `/jobs?completed=<order_no>` and the page never declared
`searchParams`, so the confirmation was a dead parameter and a submitted job simply vanished with
no acknowledgement at all.

**Keyed on `completed_at`, not on `status = 'job_done'`.** Status is the obvious filter and the
wrong one: the moment a manager approves the job it becomes `reviewed`, the row leaves the list,
and the notification link goes with it — for a reason that has nothing to do with whether the
customer was told. A prompt manager would destroy the link within minutes. The timestamp also
composes with the state machine for free, because the trigger clears `completed_at` on `rejected`,
so a bounced job drops out of this list and reappears in the open one with no special-casing
anywhere. Seven days and ten rows, both judgement calls with a cost at each end: too short and the
link expires before anyone chases it, too long and the field view quietly becomes a history page.

**`closed` is the one status still excluded**, and it is a deliberate exception rather than a hole
in the rule above. The two post-completion statuses are not equivalent. `reviewed` lands minutes
after completion, by someone else's action, while a notification may genuinely still be pending —
that is exactly the case the timestamp keying exists to survive. `closed` is terminal: reached
after review, meaning two people have already handled the order and it has left the workflow. A
technician's phone is the smallest screen in the system, and a card offering an action on a
finished order is noise under a heading that implies there is something to do.

The cost is real and is accepted rather than waved away: this reintroduces a status dependency, so
a customer ringing two days after closure to say nobody told them leaves the technician with no
link — someone else's action removed it, which is the precise failure mode timestamp keying was
introduced to prevent. It is acceptable only because closure implies the order has already passed
two people, so a genuinely missing notification surfaces through the business rather than through
this card.

The window is stated in the UI — *Recently completed · Last 7 days* — reading the same exported
constant the query uses, so the label cannot advertise a window the rows do not match. Without it,
a job dropping off after a week reads as data loss rather than a boundary.

### A confirmation is a moment; a URL is not

Completion redirects to `/jobs?completed=<order_no>`, and that parameter was doing a job it is
badly suited to. A URL is durable — it survives a refresh, the back button, a bookmark, a link
pasted into a chat — while the thing it was describing is a single moment. Left alone, the app
would still be announcing a completion as though it had just happened days later, to whoever
opened that URL.

So the parameter is **consumed**: rendered once, then stripped from the address bar with
`replaceState` on mount. The banner appears exactly once, for the arrival that earned it.

The sharper half of the same problem was the notification link itself. It carries
`target="_blank"`, so opening WhatsApp never navigates the page and never re-renders it — the
banner would still be reading *"Notify Ahmad now"* when the technician switched back from the
message they had just written. Opening the link therefore dismisses the banner.

**Dismissing is not a claim that anything was sent**, and the distinction matters given that the
whole module refuses to record delivery. Nothing is written, on the client or the server. This is
one screen forgetting a prompt it has already given, and the job keeps its own link in the list
below — so if WhatsApp never opened, the way back is untouched.

The general shape is worth naming, because it recurs: **state that describes an event should be
consumed, while state that describes a fact should be derived.** The banner is an event and gets
consumed; the notify link is a fact about the row and gets derived every render. Putting either
one in the other's category is what produces both a stale banner and a link that vanishes when a
manager clicks approve.

### What is not built, and why it is not an oversight

**The assignment notification to the technician** (Module 1's bonus) is the one place this
mechanism does not fit, so it was left out rather than demoed badly. A deep link needs a human
tap, which suits a one-at-a-time moment — a technician finishing one job, phone already in hand —
and fails at a batch one. An admin assigning twelve jobs on a Monday taps twelve links, bounces to
WhatsApp Web and back twelve times, and stops doing it by job four. A notification nobody sends is
worse than none, because the system claims a channel it does not have. Assignment is therefore the
one notification with a real case for the WhatsApp Business API and an automated send.

A related principle decided what goes *in* each message: **notify a system user with a pointer,
notify a non-user with the content.** Had the assignment message been built, it would have carried
the order number and service type and then a link into the app — not the customer's name, address
and phone. A message is a snapshot; the app is the truth, and an address corrected at 10am leaves
a stale copy in a chat log that is trusted precisely because it is immutable. Worse, that copy
puts a customer's home address permanently on two personal phones and in two chat backups, outside
anything the system controls or can delete. The customer's message is self-contained only because
the customer has no login and never will.

### Limitations, stated plainly

- **Nothing is sent until a human taps.** `wa.me` opens WhatsApp with the message typed but
  unsent. If the technician does not press send, the customer hears nothing.
- **The customer sees the technician's personal number**, not a company one, because the message
  is sent from whichever device opened the link.
- **Nothing is recorded.** Control passes to another application and never comes back, so "was it
  sent" is not a question this system can answer. Recording the click and labelling it *notified*
  was considered and rejected: it would report a fact the system does not have. The honest gap is
  better than a confident wrong answer.
- **`wa.me` is silent about bad numbers.** Phone validation accepts landlines by design — an admin
  types what is on the customer's card — and a landline produces WhatsApp's own invalid-number
  screen rather than anything this app can catch first.
- **The banner's dismissal is per-device and not persisted.** Opening the link on a phone does not
  dismiss the same banner in a desktop tab left open on the same account. Persisting it would mean
  recording a click as though it meant something, which is the thing this module declines to do.

## AI Module — the assistant

### What "controlled queries" means, and what was rejected

The spec asks for an assistant that answers "based on system data retrieved through controlled
queries" and that does "not rely on unrestricted access to the entire database." Those are two
claims, and the design turns on separating them: **the model does not author the database access,
and the model has no connection to the database at all.**

There are two jobs in "AI over a database", and neither needs database access:

| | Job A | Job B |
|---|---|---|
| In | English question | Structured result |
| Out | Which query, and what parameters | An English sentence |

The database sits *between* them, in ordinary TypeScript. That gap is the architecture.

**Text-to-SQL — rejected.** The spec forbids it, but the reason matters more than the rule: you
cannot enumerate what it might ask. It can be hardened — read-only role, statement timeout, forced
`LIMIT`, parser allowlist — and it is a real production pattern with a read replica behind it.
What it cannot give you is a finite list. Three failure modes: `select * from users` sends customer
phone numbers to a third party; a bad join pins the CPU; and, the one that actually bites, a
plausible-but-wrong query returns a confident wrong number. In an ops tool nobody checks those.

**RAG — rejected as the wrong shape, not as overkill.** Every question the spec names is an
aggregate over a filtered set with a date predicate: a count, a group-by-max, a list scoped by
technician and window. Vector similarity cannot count. "How many jobs completed today" retrieved by
nearest-neighbour returns the *k* rows that sound most like the question, and counting those is
wrong whenever the true answer exceeds *k*. RAG has a real home in this app — `work_done` and
`problem_desc` are free prose, and "which jobs mentioned a compressor fault?" is genuinely a
similarity question — but that is a different feature.

**Structured intent — chosen.** The model returns a `QueryIntent`, validated by zod, dispatched to
one of three hand-written functions. The complete set of queries this feature can run is finite,
enumerable, and visible in one file, `src/lib/ai/queries.ts`. That property *is* the definition.

### The flow

```
1. authorize        managers only, from the cookie, before anything runs
2. validate input   the question is bounded text (3–300 chars)
3. interpret        LLM #1 -> intent, parsed by zod.        NO DATABASE ACCESS
4. run              one of three hand-written queries.      NO MODEL OUTPUT
                    except two validated parameters
5. format           deterministic answer from the retrieved rows
6. narrate          LLM #2 rephrases step 5.                NO DATABASE ACCESS
```

Steps 3 and 6 are the only places a model appears. Step 4 is the only place the database appears.
They never overlap.

Implemented as a **server action**, not a route handler, to match the rest of the app — every other
write goes through `src/app/actions/*`. It gets the session cookie for free and the types flow
straight through. A route handler would be right if anything outside this app needed to ask.

### The security boundary is four boundaries

Treating it as one thing is the mistake.

1. **The API key.** `GEMINI_API_KEY` is read in server-only code, no `NEXT_PUBLIC_` prefix, same as
   the service role key. `import 'server-only'` makes an accidental client import a build error.
2. **The query surface.** Sits at the dispatcher in `runQuery`. The model emits a name and an args
   object; both are parsed by zod; an unrecognised value is a rejection, not a fallthrough. The
   principle: **model output is untrusted input** — the same treatment as a request body off the
   internet, because that is what it is.
3. **Authorization, which is not the same thing.** A perfectly controlled query set can still return
   rows the caller should not see. Checked in the page, again in the server action, and again in
   `runQuery`. The AI layer must not become a second, unscoped read path around `lib/orders.ts` —
   the same argument that scopes `getOrder` as well as `listOrders`.
4. **Exfiltration, in both directions.** *Inbound:* a prompt injection can at most make the model
   choose a different one of three operations with different parameters — the blast radius is
   bounded by (2) rather than by the model's compliance. *Outbound:* results are sent to Google, so
   **the projection is part of the control**. Every query names its columns; `JOB_FIELDS` is
   `order_no, service_type, completed_at`. No query in this module can return a customer name,
   phone, address, price, payment, uploaded document, admin note or technician remark.

### The bug that would have shipped: "completed" is not a status

The first design said `completed = status == 'job_done'`. That is wrong, and the seed data proves
it. Status moves on for reasons unrelated to whether the work was done — a manager reviews the job
and it becomes `reviewed`, then `closed`. Measured against live data:

| Window (Malaysian) | Rows with `completed_at` | With `status = 'job_done'` |
|---|---|---|
| Last week, 17–23 Aug | **10** — 7 closed, 3 reviewed | **0** |
| This week, 24–30 Aug | 13 | 10 |

So the spec's own example question, asked on 28 Aug, would have answered *"Ali completed 0 jobs last
week"* when the true answer is three. Zero, confidently, with nothing to debug.

The predicate is `completed_at is not null` and inside the window. This also composes with the state
machine for free: the trigger clears `completed_at` on rejection, so a bounced job leaves these
counts with no special-casing. Same reasoning as `listRecentlyCompleted` in `lib/jobs.ts`, which had
already reached this conclusion for the technician's view.

### "Today" means a Malaysian day

`completed_at` is `timestamptz` — an instant. "Today" and "this week" are calendar boxes, and a
calendar needs a place to be drawn. Malaysia is UTC+8, so anything completed between 16:00 and 23:59
UTC is already tomorrow in Kuala Lumpur. Supabase runs in UTC; so does Vercel.

Live in the seed on 28 Aug: **three** jobs completed today by the Malaysian calendar, **one** by the
UTC one. Two of them (ORD-01085 at 16:56Z, ORD-01079 at 16:14Z) sit in that eight-hour strip. The
bug hides all morning, appears in the evening — which is when aircon technicians finish their last
job — and only in production, because a dev machine here is already on Malaysian time.

**The model never sees or computes a date.** It picks a word from a closed list (`TODAY`,
`THIS_WEEK`, `LAST_WEEK`, `THIS_MONTH`, `ALL_TIME`) and `resolveWindow` in `src/lib/time.ts` turns
that into two absolute instants. Letting the model emit `{from, to}` would hand date arithmetic to a
thing that is bad at it, does not know today's date, and does not know the company is in Malaysia.

Three implementations considered:

- **Calendar maths in Postgres** — correct, but PostgREST cannot express `at time zone` twice, so it
  needs an RPC and a ninth migration, breaking the `db.from(...)` convention used everywhere else.
- **A generated `completed_on_myt` column** — not available: `timestamptz at time zone` is `STABLE`,
  not `IMMUTABLE`, because it depends on the tz database.
- **Resolve in TypeScript, pass two instants to PostgREST** — chosen. Half-open `[from, to)` so a job
  completed at exactly midnight lands in one box, not both and not neither. The resolver is a pure
  function of `(period, now)`, which is what makes it testable at all.

`OFFSET_MS` is a constant rather than derived from the IANA name at runtime, and that is a deliberate
reversal. The `Intl` derivation *looks* more principled and is subtly wrong twice: `formatToParts` is
second-precision, so reconstructing the instant loses the milliseconds and reports the offset as
7.99998 hours; and the technique is only correct for fixed-offset zones anyway, because in a DST zone
the offset at `now` differs from the offset at midnight. It is a special case wearing a general
costume. The honest special case is a constant plus a test asserting it still agrees with `TZ`.

The assumption, stated: **Malaysia has no DST and has been fixed at +08:00 since 1982** — before
that, +07:30, so a completion timestamped pre-1982 would be half an hour wrong. None exist. A
business spanning timezones needs `Temporal` or a tz library.

**The same bug was already in this repo.** The verification block at the bottom of `seed.sql` used
`current_date` and `date_trunc('week', now())`, both UTC, and reported "today: 1" while the header
comment above it claimed 3 — which is what the seed was built to produce. The comment and the query
disagreed, and the query was wrong. Fixed in the same commit.

### Testing the resolver, and checking the test could fail

Nine assertions in `src/lib/time.test.ts`, run with `npm test`. No framework: Node runs TypeScript
directly and ships `node:test`, so this cost nothing to install — the same reasoning that made the
state machine a plain SQL script instead of pgTAP.

Two ways this test could have silently proved nothing, both avoided deliberately:

- **Computing the expectation with the implementation's own arithmetic.** Every expected value is a
  hand-typed ISO string, worked out on paper. A test that derives its expectation passes even when
  the implementation is wrong.
- **Pinning the clock outside the divergence strip.** The clock is fixed at `2026-08-27T16:56:16Z` —
  a real `completed_at`, ORD-01085 — which is 28 Aug 00:56 in Kuala Lumpur. Only between 16:00 and
  23:59 UTC do the two calendars name *different days*, so a clock at, say, 08:29Z would let every
  label assertion pass under a UTC implementation.

**Mutation check.** Setting `OFFSET_MS = 0` was predicted to red seven assertions and leave two
green — the half-open week join, which asserts a *relationship* between edges that move together, and
the ALL_TIME rejection, which contains no date. That is exactly what happened; the prediction was
written before the run.

One prediction was wrong: `en-MY` abbreviates September as **"Sept"**, not "Sep". The expectation was
wrong, not the code.

### What can be asked, and what happens otherwise

Three operations — `LIST_JOBS`, `COUNT_JOBS`, `RANK_TECHNICIANS` — filtered by technician name,
service type and period. `COUNT_JOBS` is not strictly necessary, since `LIST_JOBS` returns a count
too; it earns its place by **not shipping rows**, using `head: true` so a count question sends zero
order data to the model.

The model's response is an envelope, not a bare intent:

```ts
{ supported: true,  intent: {...} }
{ supported: false, reason: "..." }
```

A schema that only describes an intent *forces* the model to produce one for every input — asked
about a refund policy it would invent a `LIST_JOBS`. Making "I can't answer that" a first-class typed
outcome is how the module handles being asked something it has no query for.

`dateRange` is **required**. Optional, an absent value would have to mean both "the manager meant all
time" and "the model forgot", and those cannot be told apart — so a dropped field on "how many
today?" would silently answer for all time. Same reasoning as `ALL_STATUSES` in `lib/types.ts`.

An unknown technician returns a **structured** miss — `{ kind: 'UNKNOWN_TECHNICIAN', known: [...] }` —
not an empty result set. "Ali completed 0 jobs" for a technician who does not exist is a confident
wrong answer. Even the failure path is generated from structured data.

### Two answering layers, and why both exist

`formatAnswer` produces the answer deterministically from the query result. `narrate` asks the model
to rephrase **that sentence** — it never receives rows, so there is no arithmetic left to get wrong.
If the model call fails or times out, the deterministic answer ships and the UI says so.

**The prose layer is decorative. Delete it and the system still answers correctly, just less
fluently.** Every number in every answer came out of Postgres.

That was observed working unprompted during testing: an unknown-technician question came back
correctly phrased by `formatAnswer` with the note "the AI phrasing step was unavailable", because the
second model call had failed.

`narrate` was initially given the full `QueryResult` as well. It pasted raw instants into the reply —
*"for the window from 2026-08-27T16:00:00.000Z to…"* — because they were in front of it and looked
relevant. Removing it produced a better answer and sent less data out of the building.

**An honest observation.** On `RANK_TECHNICIANS` the model frequently returns the deterministic
sentence byte-for-byte, so the second call cost a request and changed nothing. On `LIST_JOBS` it does
edit — the template's "(17–23 Aug 2026)" becomes "between 17–23 Aug 2026". The step is kept because
the spec's flow diagram ends with "AI formats the response", but it earns less than it looks like it
does.

### Choosing the model, by measurement

Model ids were not assumed. Each candidate was called with this module's real schema and prompt, and
timed:

| Model | Result |
|---|---|
| `gemini-2.5-flash` | retired — "no longer available to new users" |
| `gemini-3.7-flash` | "currently experiencing high demand" |
| `gemini-3.5-flash` | ~3s, correct |
| `gemini-3.6-flash` | **~39s**, correct — reasons at length about a three-way classification, and rejects `thinkingBudget: 0` with a 400, so the thinking cannot be turned off |
| `gemini-3.1-flash-lite` | ~1s, correct intent — **used for interpret** |
| `gemini-3.5-flash-lite` | ~1s, correct phrasing — **used for narrate** |

The lite tier winning is not a compromise. Choosing between three operations and copying a name
across is not a reasoning problem, and paying 39 seconds of chain-of-thought for it buys nothing.

Both are pinned rather than `-latest`: a model that silently changes under a submitted assessment is
a demo that cannot be reproduced.

**Two different models, for a quota reason rather than a capability one.** The Gemini free tier
allows 20 requests per day *per model*. One question costs two calls, so a single model would cap the
feature at ten questions a day — found the hard way, by exhausting `gemini-3.5-flash` during testing
and watching every question start returning an outage. Splitting the calls across two models doubles
the budget for free. On a paid key both constants would be the same model.

### Debugging notes worth keeping

The catch around `interpret` originally had no logging, so a provider outage, a quota rejection and a
bug in our own parsing all reached the user as one sentence with nothing behind it. Adding one
`console.error` is what made the 39-second model visible at all — the log said `AI request timed out`
at 12.4s, which pointed at latency, not quota. Quota exhaustion and an outage now produce different
messages, because the difference is actionable: one resets tomorrow, the other may clear in a minute.

### The window floats

The question a manager asks is almost always prompted by something they are already looking at.
Sending them to a separate route costs them the list they were reading. A floating button opens a
panel over the current screen; `/ask` still exists as a linkable full-page version.

The prose answer and the table under it come from **two different sources on purpose** — the sentence
is the model's phrasing, the table is rendered straight from the returned rows. If the model ever
miscounts or invents an order number, the authoritative list is directly beneath it.

### Verified against real data

All three of the spec's example questions, run in the app:

| Question | Answer | Cross-checked |
|---|---|---|
| What jobs did Ali complete last week? | 3 — ORD-01053 Cleaning, ORD-01067 Installation, ORD-01068 Cleaning | ✅ |
| Which technician completed the most jobs this week? | Bala 6 (Ali 4, John 2, Yusoff 1) | ✅ |
| How many jobs were completed today? | **3** — a UTC implementation says 1 | ✅ |

Each was checked independently against PostgREST with the same bounds before the UI existed.

### Limitations, stated plainly

- **Three operations only.** No trends, no comparisons between two periods, no "why", no revenue or
  price questions — pricing is deliberately outside the projection. Anything else is refused with a
  sentence saying what *can* be asked.
- **The period vocabulary is a closed list.** "In June" and "between the 3rd and the 10th" cannot be
  expressed. Extending it is one enum value and one `case`, but it is not extensible by the model at
  runtime, which is the point.
- **`LAST_WEEK` means the previous Monday–Sunday**, not the trailing seven days. Some managers mean
  the other thing. Mitigated by printing the resolved window in every answer.
- **Name resolution is by string match.** Two technicians called Ali return an ambiguity prompt
  rather than a guess, but there is no employee ID to disambiguate with — `users.name` is the only
  handle the schema offers.
- **No conversation memory.** Each question is independent; "and what about John?" will not work.
- **20 requests per model per day** on the free tier, so roughly 20 questions a day across the two
  models. A demo key, not a production one.
- **No rate limiting, quota guard or cost cap of our own.** A manager holding the return key costs
  money.
- **Roughly 2–3 seconds per answer**, two sequential model calls. Dropping `narrate` would nearly
  halve it.
- **The model is a third party.** Order numbers, service types, completion timestamps and technician
  first names are sent to Google. Customer and payment data never is, by construction.
- **`formatAnswer` has no unit test.** It is pure and trivially testable; every branch has been
  exercised by hand through the UI, but nothing would catch a regression. The clearest gap in this
  module.
- **Authorization still rests on the role switcher.** As everywhere else in this app, the manager
  check validates a role the client asserts. With real auth it becomes a genuine boundary.
